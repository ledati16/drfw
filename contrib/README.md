# DRFW Contrib Files

This directory contains distribution packaging and system integration files.

## Contents

- `PKGBUILD` - Arch Linux package build file (fill in the `Maintainer` line)
- `drfw.service.in` - template of the systemd service for boot-time firewall; the
  installed `drfw.service` is generated with `drfw print-service-unit` (see below)
- `org.drfw.helper.policy.in` - template of the polkit action for the root helper; the
  installed `org.drfw.helper.policy` is generated with `drfw print-polkit-policy`
- `drfw.desktop` - Desktop entry for application menus
- `icons/` - application icons (`drfw-<size>.png` to install, `drfw.svg` is the
  editing source only; see `icons/README.md`)

## Arch Linux (PKGBUILD)

Build and install from source using the provided PKGBUILD:

```bash
cd contrib
makepkg -si
```

This installs:
- `/usr/bin/drfw` - the main binary
- `/usr/lib/drfw/drfw-helper` - the root helper, the only program DRFW elevates
- `/usr/share/polkit-1/actions/org.drfw.helper.policy` - its polkit action, generated by
  the built binary with `drfw print-polkit-policy`
- `/usr/share/applications/drfw.desktop` - desktop entry
- `/usr/share/icons/hicolor/<N>x<N>/apps/drfw.png` - icons, N = 16 24 32 48 64 128 256 512
- `/usr/lib/systemd/system/drfw.service` - systemd service (not enabled), generated by
  the built binary with `drfw print-service-unit`
- `/usr/share/licenses/drfw-git/LICENSE` - license file

`build()` and `check()` set `DRFW_SYSTEM_NFT_PATH=/etc/nftables.conf`,
`DRFW_SYSTEM_NFT_SERVICE=nftables.service`, `DRFW_NFT_PATH=/usr/bin/nft` (Arch's
layout) and `DRFW_HELPER_PATH=/usr/lib/drfw/drfw-helper`. `check()` runs `cargo test` as the build user. It needs `jq` (for the mock nft)
and uses the real `nft` only inside an unprivileged user + network namespace
(`unshare -rn`); where that is unavailable those tests skip themselves.

### Prompts

DRFW elevates only its root helper, `/usr/lib/drfw/drfw-helper`, through the polkit
action `org.drfw.helper`. The dialog says "Authentication is required to change the
firewall rules". The action's defaults are `auth_admin_keep` for the active local
session (`auth_admin` for remote and inactive sessions, which are asked every time), so
on a desktop polkit remembers the password for about five minutes, for the DRFW process
that asked only:

| Operation | Prompts |
|-----------|---------|
| Verify (before Apply) | none normally (checked in a private namespace); the elevated `check` only if that check is inconclusive |
| Apply (GUI) | one; none if this window authenticated in the last ~5 minutes |
| Save to System (GUI) | one, or none within ~5 minutes (enabling the boot service runs in the same request) |
| `drfw apply`, `drfw save` (CLI) | one per command: `sudo` keeps its own timestamp (5 minutes per terminal by default), `run0` and `pkexec` (a new process each time) ask each time |
| Confirm, auto-revert, "revert now" | none (handled by the root-side guard started by Apply) |
| Boot persistence check (dialog, `drfw status`) | none (`systemctl is-enabled`/`is-active` as your user) |

Why remembering is safe for the helper: it is not a shell. It accepts three fixed
requests (apply with the revert guard, save the boot config, check a ruleset), checks
every argument against the paths this build was compiled with, passes nothing from the
caller's environment on (`PATH=/usr/sbin:/usr/bin:/sbin:/bin` only), and refuses
rulesets in which `nft` could read another file (`include`). Remembering `/bin/sh`
would allow any root command, and remembering root `nft` would let anything that
drives DRFW read any file (`nft -c -f <file>` echoes it in errors). Older versions
shipped a polkit **rule** for `nft`; DRFW ships none and needs none. Do not add one,
and do not add a sudoers `NOPASSWD` entry for the helper.

Without an installed helper (a build run from the source tree), DRFW elevates
`/bin/sh` with the same fixed scripts and every elevated operation asks.

## Generating the polkit action

`org.drfw.helper.policy.in` contains `@HELPER_PATH@`. Generate the action from the
built binary, so it names exactly the helper path it elevates (`DRFW_HELPER_PATH`,
default `/usr/lib/drfw/drfw-helper`):

```bash
target/release/drfw print-polkit-policy > org.drfw.helper.policy
install -Dm644 org.drfw.helper.policy "$pkgdir/usr/share/polkit-1/actions/org.drfw.helper.policy"
install -Dm755 target/release/drfw-helper "$pkgdir/usr/lib/drfw/drfw-helper"
```

The helper must end up owned by root and not group- or world-writable, in directories
that are not either; otherwise DRFW does not use it.

## Generating drfw.service

`drfw.service.in` contains `@SYSTEM_NFT_PATH@` and `@NFT_PATH@`. Do not fill them in
with `sed`: the built binary prints the unit with its own compile-time values, so the
unit always loads the file Save to System writes:

```bash
target/release/drfw print-service-unit > drfw.service
install -Dm644 drfw.service "$pkgdir/usr/lib/systemd/system/drfw.service"
```

`@NFT_PATH@` is `DRFW_NFT_PATH`, or `/usr/sbin/nft` when unset. The command is hidden
from `--help`, needs no privileges and creates no files. The unit is ordered
`Before=network-pre.target` with `Wants=network-pre.target` (see
[Option 2](#option-2-drfwservice-drfw-alternative)).

The version shown by `drfw -V` and the GUI includes the git commit only when building
from a checkout (as `PKGBUILD` does). A build from a release tarball or other source
without `.git` reports plain `0.9.0`, with commit and branch `unknown` in
`drfw --version`.

## Per-Distribution Settings

| Distribution | `DRFW_SYSTEM_NFT_PATH` | `DRFW_SYSTEM_NFT_SERVICE` | `DRFW_NFT_PATH` | Notes |
|--------------|------------------------|---------------------------|-----------------|-------|
| Arch | `/etc/nftables.conf` | `nftables.service` | `/usr/bin/nft` | What `PKGBUILD` uses |
| Debian / Ubuntu | `/etc/nftables.conf` | `nftables.service` | `/usr/sbin/nft` | `/usr/sbin` may not be on users' `PATH`; Ubuntu also ships `ufw` |
| Fedora / RHEL | `/etc/sysconfig/nftables.conf` | `nftables.service` | `/usr/sbin/nft` | The stock file is `include` lines; it is kept as `.drfw-orig`. `firewalld` is on by default |
| openSUSE | check your distro | check your distro | `/usr/sbin/nft` | `firewalld` is the usual default |
| NixOS | (declarative) | (declarative) | `/run/current-system/sw/bin/nft` | Prefer `drfw export` into `networking.nftables.ruleset`; see the main README |

Details and caveats: "Packaging" in the main [README](../README.md).

## Boot-Time Firewall

### Option 1: nftables.service (System Standard)

Use the standard nftables service with DRFW's export feature:

1. Configure your rules in DRFW
2. Click **Save to System** (writes `/etc/nftables.conf`; the previous file is kept as
   `/etc/nftables.conf.drfw-bak`, and the file DRFW first replaced as `.drfw-orig`).
   The dialog shows whether `nftables.service` is enabled; if it is not, keep **Also
   enable nftables.service at boot** checked and it is enabled in the same prompt.
   On a headless server: `drfw apply <profile>`, confirm, then
   `drfw save <profile> --enable-at-boot` (same script, one prompt).
3. Or enable it by hand (`start` also loads the rules now; DRFW itself only enables):

```bash
sudo systemctl enable nftables.service
sudo systemctl start nftables.service
```

**Note:** `nftables.service` flushes the entire ruleset on stop, which may affect other tables (docker, libvirt, etc.). Loading DRFW's file itself only replaces the `inet drfw` table.

### Option 2: drfw.service (DRFW Alternative)

The `drfw.service` is an alternative to `nftables.service` that only manages the DRFW table:

1. Configure your rules in DRFW
2. Click **Save to System** (writes the build's `DRFW_SYSTEM_NFT_PATH`, by default
   `/etc/nftables.conf`, the file the generated `drfw.service` loads)
3. Enable the DRFW service (with the default build, the dialog's checkbox enables
   `nftables.service` instead; DRFW counts an enabled `drfw.service` as loading the
   rules at boot and then does not offer it):

```bash
sudo systemctl enable drfw.service
sudo systemctl start drfw.service
```

**Key difference:** On stop, `drfw.service` only deletes the `inet drfw` table, preserving other tables like docker or libvirt.

Like a firewall unit should, `drfw.service` is ordered `Before=network-pre.target`
(with `Wants=network-pre.target`), so the rules are loaded before NetworkManager or
systemd-networkd bring up any interface: there is no unfiltered window at boot.

The file DRFW writes begins with `table inet drfw` / `delete table inet drfw`, so
start and reload replace the drfw table atomically and never duplicate rules.
`drfw status` shows whether `/etc/nftables.conf` was written by DRFW and which unit
loads it at boot ("Boot persistence"); if it was not written by DRFW (e.g. a distribution default starting with `flush ruleset`), `drfw.service`
would load it as it is.

### Service Commands

```bash
# Check service status
systemctl status drfw.service

# View service logs
journalctl -u drfw.service

# Reload firewall rules (after Save to System)
sudo systemctl reload drfw.service

# Stop the firewall (removes drfw table only)
sudo systemctl stop drfw.service

# Disable boot-time loading
sudo systemctl disable drfw.service
```

## Comparison: nftables.service vs drfw.service

| Feature | nftables.service | drfw.service |
|---------|------------------|--------------|
| Config source | the distribution's file (`/etc/nftables.conf` on Arch/Debian) | `DRFW_SYSTEM_NFT_PATH` (filled in by `print-service-unit`) |
| On start/reload | Loads the file (DRFW's replaces only `inet drfw`) | Same |
| Boot ordering | set by the distribution's unit | `Before=network-pre.target` |
| On stop | Flushes entire ruleset | Deletes only `inet drfw` table |
| Other tables | Removed on stop | Preserved on stop |
| Conflicts with | drfw.service | nftables.service |
| Recommended for | Single-purpose firewall | Systems with docker/libvirt/etc. |

## Troubleshooting

**Service fails to start:**
```bash
# Was the file written by DRFW? (no root needed)
drfw status

# Check if nftables.conf exists
sudo cat /etc/nftables.conf

# Test loading manually
sudo nft -f /etc/nftables.conf

# Check for syntax errors
sudo nft -c -f /etc/nftables.conf
```

**Firewall not applying:**
```bash
# View detailed logs
journalctl -u drfw.service -n 50

# List current ruleset
sudo nft list ruleset

# Verify drfw table exists
sudo nft list table inet drfw
```
